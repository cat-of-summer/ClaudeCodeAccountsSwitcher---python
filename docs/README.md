# ccas — Claude Code Accounts Switcher

Переключение между несколькими аккаунтами Claude Code. Один самодостаточный бинарник для Windows, Linux и macOS: ставит себя сам, перехватывает вызов `claude` через PATH и подменяет **только учётные данные**.

История, проекты, настройки, плагины и всё остальное в `~/.claude` остаются общими для всех аккаунтов.

## Как это работает

Claude Code читает путь к файлу кредов из отдельной переменной окружения:

```js
// claude v2.1.218
function KK(){ let e = process.env.CLAUDE_SECURESTORAGE_CONFIG_DIR;
  if (e !== void 0) return (e || join(homedir(), ".claude")).normalize("NFC");
  return cn(); }                        // -> join(KK(), ".credentials.json")
```

`CLAUDE_SECURESTORAGE_CONFIG_DIR` переносит **только** `.credentials.json` — в отличие от `CLAUDE_CONFIG_DIR`, который утащил бы за собой историю и проекты. Поэтому каждый слот получает свой каталог кредов, а всё остальное остаётся общим:

```
~/.claude/                        ← общее: projects/, history.jsonl, settings.json, plugins/
~/.claude.json                    ← общее, патчится только oauthAccount + userID

~/.claude-switcher/creds/1/.credentials.json   ← слот 1
~/.claude-switcher/creds/2/.credentials.json   ← слот 2
```

Побочный, но важный эффект: копировать креды туда-сюда больше не нужно, поэтому **два терминала на разных аккаунтах работают одновременно** и не затирают токены друг друга.

Одна ячейка всё же остаётся общей: `oauthAccount` в `~/.claude.json`. Её перезаписывает каждый запускающийся claude, так что к моменту закрытия первого окна там лежит аккаунт второго. Раньше ccas на выходе забирал найденное там себе в слот — и закрывающееся окно уносило чужой аккаунт, после чего оба слота схлопывались в один.

Теперь совпадение `accountUuid` с уже известным для слота принимается сразу, а незнакомый принимается только если он ничей, никакая другая обёртка в этот момент не запущена и креды самого слота были записаны в течение сеанса. Первое условие отсекает соседний слот, второе — гонку двух окон, третье — случайное подхватывание. Законный перелогин слота под другим аккаунтом все три условия проходит.

Живые сеансы отмечаются файлами `~/.claude-switcher/sessions/<pid>.json`; записи умерших процессов подчищаются при следующей проверке.

По той же причине стор аккаунтов никогда не сохраняется из снимка, прочитанного при старте: сеанс claude живёт часами, а за это время соседние окна и команды `ccas` успевают его поменять. Любая правка перечитывает `accounts.json` под межпроцессной блокировкой и пишет только своё поле — иначе выходящее окно откатывало чужой `ccas rename`.

Если установленная сборка claude эту переменную не понимает, ccas автоматически переходит в режим копирования. Там общий файл кредов физически один на всех, поэтому второй слот не стартует, пока открыт первый: ccas сообщает, какой слот занят, вместо того чтобы затереть его токены.

## Установка

Требуется уже установленный Claude Code. Права администратора не нужны — всё кладётся в домашний каталог, PATH правится только на уровне пользователя.

```bash
# Windows
.\ccas-windows-x64.exe install

# Linux
./ccas-linux-x64 install
```

Установщик найдёт оригинальный `claude`, определит режим кредов и язык интерфейса, спросит про `--dangerously-skip-permissions` и автосмену аккаунта, перенесёт существующий стор из `~/.claude-accounts` и подхватит текущий вход как слот.

После установки **открой новый терминал**, чтобы PATH обновился.

## Использование

```bash
claude                  # последний использованный аккаунт, без вопросов
claude 2                # запустить на слоте 2
claude 2 -p "привет"    # слот 2 с аргументами
claude @work            # по алиасу
claude -- 2             # промпт "2", а не слот
claude mcp list         # подкоманды пробрасываются как есть
```

Обёртка забирает **только первый токен** и только если он целиком из цифр или начинается с `@`. Всё остальное уходит в claude без изменений; единственное вмешательство в аргументы — подмешивание `--dangerously-skip-permissions`, если он выбран при установке и не задан вручную.

Алиасы требуют префикса `@` намеренно: иначе `claude work` съел бы однословный промпт вместо того, чтобы отправить его в claude.

Голый `claude` не спрашивает ничего: берётся активный слот, а если в нём нет логина — самый недавно использованный из тех, где логин есть. Выбор аккаунта живёт в `ccas list` и `ccas menu`.

### Управление

```bash
ccas list [--refresh|--cached]  # аккаунты и лимиты
ccas menu                       # выбрать аккаунт и сразу запустить на нём claude
ccas run 2 | @work [args…]      # то же без меню
ccas switch 2 | @work           # только сменить активный слот
ccas rename 2 work              # задать алиас
ccas add                        # подсказать свободный слот
ccas remove 2                   # удалить слот вместе с токенами
ccas usage [--cached]           # лимиты по всем аккаунтам
ccas config [ключ [значение]]   # посмотреть и изменить настройки
ccas doctor                     # диагностика установки
ccas install                    # накат новой версии поверх текущей
ccas reinstall                  # то же, но с вопросами о настройках
ccas uninstall [--purge]        # снять перехват; --purge удаляет и токены
```

`ccas list` показывает сохранённые лимиты и молча обновляет по сети устаревшие. `--refresh` опрашивает все принудительно, `--cached` не ходит в сеть вовсе.

Голый `ccas` открывает свою командную строку: список из кэша появляется сразу, сеть опрашивается по `r`. Номер слота (`2`) или `go 2` запускает на нём claude прямо в этом окне; то же делает Enter в `ccas menu`. Запуск идёт через ту же обёртку, что и `claude 2` — с супервизией и автосменой, — а по выходе из claude возвращается приглашение `ccas>`.

Окно, у которого момент отката уже прошёл, показывается пустым, сколько бы процентов ни лежало в сохранённом снимке: пятичасовое окно успевает откатиться быстрее, чем снимок устаревает.

Имя слота — email из профиля аккаунта. Раньше он брался только из общего `~/.claude.json` и только при закрытии сеанса, а к тому моменту файл обычно принадлежал соседнему окну, и слот оставался «слот 3». Теперь безымянному слоту email добывается по его же токену (`/api/oauth/profile`) при первом обновлении лимитов, а без сети — из `identity/<n>.json`.

У каждого окна своя дата и время отката в локальной зоне: `5ч 46% ↻ 05.08 18:50 · 7д 96% ↻ 12.08 09:00`.

Лимиты аккаунта, которым давно не пользовались, всё равно приходят: access-токен живёт часы, но ccas сам меняет его по refresh-токену перед запросом. Аккаунт, которому нужен повторный вход, честно об этом пишет, а протухший access-токен ничего не значит и цифры не заслоняет.

### Настройки

```bash
ccas config                              # экран правки (или список в пайпе)
ccas config skip-permissions off
ccas config auto-switch on
ccas config auto-switch-max-wait 90
ccas config auto-switch-prompt "Продолжай"
```

Переустанавливаться ради смены настройки больше не нужно.

### Автосмена аккаунта

Выключена по умолчанию. Включённая, она делает то же, что вы делаете руками, когда кончилась квота: выйти из claude, переключить аккаунт, вернуться в тот же разговор через `--resume`.

Момент перехода определяется не опросом API, а фактом: claude записывает в транскрипт сессии строку с `"error":"rate_limit"`, когда действительно упёрся в стену. До этого он может часами гонять длинный инструмент — прерывать его нельзя, и ccas не прерывает. В той же записи лежит `quotaLimits` с окном (`rateLimitType`) и моментом отката (`resetsAt`) — ccas берёт их оттуда, а не угадывает по английскому тексту сообщения.

Дальше ccas сверяется с API (временный 429 в транскрипте выглядит так же, как исчерпанная квота), заново опрашивает лимиты **всех** кандидатов — снимок из стора здесь не годится, пятичасовое окно откатывается быстрее, чем он устаревает, — выбирает наименее нагруженный аккаунт со свободными лимитами и перезапускает сессию на нём: с тем же id разговора, в том же режиме, включая plan, и с сообщением из `auto-switch-prompt`, чтобы работа продолжилась без напоминания.

Свободных нет — ccas находит слот, который откроется раньше всех (это может быть и текущий, и уже пробованный в этом сеансе), останавливает claude, ждёт этого момента и поднимает сессию на нём. Пробованный слот, чьё окно успело перевернуться, при этом считается свободным и берётся без ожидания. Ожидание ограничено `auto-switch-max-wait`; Ctrl+C во время ожидания выходит. Если ждать дольше лимита, сессия остаётся как есть, а причина — в журнале.

Пока claude на экране, ccas в терминал не пишет ничего: строка, попавшая под TUI, ломает отрисовку. Что происходит, видно в заголовке окна терминала, а полная история — в `~/.claude-switcher/logs/ccas.log`, включая причину каждого отказа от перехода (`unconfirmed`, `not_exhausted`, `no_target`, кулдаун). Строка в терминал печатается только между запусками, когда экран свободен.

Отказ от перехода не выключает наблюдение: следующий 429 в том же сеансе рассматривается заново.

Несколько открытых терминалов на одном аккаунте упираются в стену почти одновременно. Чтобы они не разъехались по разным аккаунтам, первый записывает `switch-plan.json`, а остальные ему следуют — и ждут того же момента, если план ждёт.

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `auto-switch` | выкл | включить всё это |
| `auto-switch-strategy` | `limits` | `limits` — наименее нагруженный; `order` — по кругу; `notify` — только напечатать команду |
| `auto-switch-threshold` | 95 | с какой загрузки пятичасового окна аккаунт считается исчерпанным |
| `auto-switch-max` | 3 | сколько переходов подряд разрешено за сеанс |
| `auto-switch-max-wait` | 120 мин | сколько ждать ближайшего отката, когда исчерпаны все; 0 — не ждать |
| `auto-switch-confirm` | вкл | сверять исчерпание с API |
| `auto-switch-restore-mode` | вкл | вернуть `--permission-mode` после перезапуска |
| `auto-switch-prompt` | «Если запускал процессы, проверь их статус, при необходимости перезапусти их и агентов, продолжай работу.» | что отправить в восстановленную сессию сразу после перехода; пусто — ничего |

Супервизия не включается там, где перезапуск за спиной вызывающего недопустим: `-p`, пайпы, `--bg`, `--cloud`, подкоманды claude и любой не-TTY.

### Хуки claude

Каждой сессии, которую запускает обёртка — интерактивной и headless, — ccas подкладывает файл настроек (`--settings sessions/<pid>.settings.json`), в котором все события claude (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Notification`, `Stop`, `StopFailure`, `SubagentStart`, `PreCompact`, … — полный список в [core/hookbus.py](core/hookbus.py.md)) направлены хуком типа `http` на локальный порт обёртки. `~/.claude/settings.json` пользователя не трогается; если пользователь передал свой `--settings`, его файл сливается с нашим (его ключи сверху, хуки — рядом).

Почему не `command`-хук: ccas собирается в один файл PyInstaller и стартует около секунды, а хук стоит перед каждым вызовом инструмента. HTTP на loopback отвечает за миллисекунды и не порождает процессов.

Что делает обёртка с событиями:

- подписчики внутри процесса — так Telegram-транспорт узнаёт о лимите (`StopFailure` с `error: rate_limit`);
- **внешние обработчики** из конфига: `ccas hooks add <событие> "<команда>" [--matcher <regex по инструменту>] [--sync] [--timeout N]`. JSON события приходит команде в stdin, в окружении `CCAS_HOOK_EVENT`, `CCAS_SESSION_ID`, `CCAS_SLOT`. `--sync` заставляет ждать команду и отдать её stdout claude как ответ хука — так можно запретить вызов инструмента (`{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", …}}` или просто код выхода 2 с причиной в stderr, как у самого claude). Без `--sync` команда работает в фоне, её вывод никуда не идёт;
- одна строка на событие в `ccas.log`.

Ещё один встроенный подписчик держит артефакты локальными: публикацию через инструмент `Artifact` он отклоняет, и агент называет путь к файлу вместо ссылки на claude.ai (сам инструмент остаётся — отдельного режима «только файлом» у claude нет). Включить публикацию обратно — `ccas config artifact-publish on`.

`ccas config hooks-bus off` выключает всё это, включая запрет публикации; `--bare` и `--safe-mode` на стороне claude отключают хуки сами, и обёртка их для таких запусков не поднимает.

### Telegram-транспорт

`claude -t telegram` запускает claude не в терминале, а в чате: сообщения из разрешённого чата уходят в сессию, ответы, вопросы (`AskUserQuestion`) и запросы разрешений приходят обратно — вопросы кнопками. Окно консоли при этом остаётся, но только как журнал; управляют сессией из Telegram.

Под капотом — не перехват TUI, а официальный протокол: `claude -p --input-format stream-json --output-format stream-json --permission-prompt-tool stdio`. Процесс живёт между ходами, сообщения ходят JSON-строками, а вопросы и разрешения claude сам присылает как `control_request: can_use_tool` и ждёт `control_response` — ровно так им управляет Agent SDK. Аргументы claude собираются из трёх источников и в этом порядке: `args` профиля, то, что набрано при запуске, `defaultArgs` из `ccas config` — так что `--dangerously-skip-permissions` из настроек действует и здесь; `AskUserQuestion` при этом всё равно доходит. Драйвер — [app/transport/driver.py](app/transport/driver.py.md), кнопки — [app/transport/prompter.py](app/transport/prompter.py.md).

#### Профиль — единица настройки и запуска

По умолчанию не слушается ничего. Что слушать, где работать и кого пускать, говорит **профиль**. У профиля числовой **id** (его называют в `ccas profile set` и `claude -t telegram -P`) и **алиас** — слово, с которого начинается обращение в чате: `/rik собери проект`. Алиас может повторяться: два проекта в двух разных чатах могут оба отзываться на `/rik`, и какому достанется строка, решает чат, из которого она пришла.

| Поле | По умолчанию | Что значит |
|---|---|---|
| `alias` | — | слово обращения в чате (`/alias`); буквы, цифры, `. _ -`, до 32 символов |
| `chats` | пусто | чаты профиля; пусто — любой чат, где есть бот. Элемент — `-100500` или `-100500:7` (чат с топиком) |
| `cwd` | домашний | рабочий каталог сессий профиля |
| `slot` | активный | аккаунт, на котором работать |
| `daemon` | выкл | может ли демон поднять профиль сам, по обращению в его чате |
| `multi` | выкл | одна сессия на весь чат (вкл) или своя на каждого участника (выкл) |
| `debug` | выкл | показывать в чате вызовы инструментов, смены режима, статистику хода и оставлять отвеченные запросы разрешений; выкл — только ответы агента, а лог инструментов остаётся в окне консоли |
| `expanded` | выкл | сообщение на каждый блок текста (вкл) или одно сообщение на ход, перезаписываемое (выкл) |
| `mode` | пусто | режим разрешений при старте; пусто — тот, в котором claude запустился бы сам |
| `users` | пусто | сужение глобального `telegram.users` |
| `args` | пусто | аргументы claude, добавляемые к каждому запуску |

```bash
ccas profile add rik --cwd O:\Projects\RIKROOT --chat -5595440781   # печатает id, например 1
ccas profile add rik --cwd O:\Projects\OTHER --chat -100500           # тот же алиас в другом чате: id 2
ccas profile set 1 --daemon on --multi on     # поднимать сам, общая сессия на чат
ccas profile set rik --alias root             # по алиасу — только пока он один
ccas profile list
```

Кому достаётся сообщение — решается один раз, в [routing.route](app/transport/routing.py.md): **`/алиас` первым словом**, и это единственный вход. Не назвали — профиль не слышит, в том числе в собственном чате; так разговор и заканчивают. Среди профилей с одним алиасом сначала берутся те, что назвали этот чат, иначе те, у кого `chats` пуст; если и после этого их несколько, демон так и отвечает — со списком `alias#id`, не гадая. Строка без известного алиаса не для агента вовсе; демон читает её как одну из своих команд (`/claude`, `/projects`, …) — и только в чатах, где хоть один профиль работает.

#### Как выглядит переписка

По умолчанию чат получает только текст агента. Один ход пользователя — одно сообщение, которое **перезаписывается** по мере работы: промежуточные рассуждения сменяют друг друга, в конце остаётся итог. Удалили это сообщение — следующее обновление придёт новым.

Каждый ответ агента начинается с метки режима, в котором он написан (🔴 bypass, 🟡 plan, 🔵 acceptEdits, 🟣 auto, ⚪ спрашивает). Отдельного приветствия при подъёме профиля нет: метка и так на виду, а что она значит и как переключать — в `/help`. У вопросов, планов и запросов разрешений свои значки, метка режима им не добавляется.

Вопросы агента и план — отдельные сообщения со своей клавиатурой; ответ дописывается в то же сообщение под вопросом, так что в чате остаётся запись «что спросили — что решили», а рабочее сообщение пересоздаётся ниже. Запрос разрешения на инструмент и форма MCP-сервера после ответа **удаляются** (при `debug: on` остаются с дописанным ответом), и рабочее сообщение тогда никуда не двигается.

Если агент написал план текстом, рабочее сообщение с ним закрывается в момент, когда приходит `ExitPlanMode`: план остаётся в чате как есть, а работа после одобрения идёт уже в новое сообщение. Иначе первый же шаг затёр бы то единственное, к чему возвращаются потом.

`debug: on` добавляет строки `🔧 Bash …`, вывод инструментов, `⏱ … · $…` и смены режима, которые claude сделал сам. `expanded: on` возвращает россыпь сообщений.

#### Режимы

Режим виден в метке каждого ответа агента, в `/status` и в `/help`: 🟡 plan, ⚪ спрашивает, 🔵 acceptEdits, 🟣 auto, 🔴 bypass. Переключают `/plan`, `/bypass`, `/auto`, `/edits`, `/ask` (и `/mode <имя>` для остальных); ответом приходит «🟡 Выбранный режим: plan», а если за командой шёл промт — «…, начинаю работу…». Какой режим будет при старте, известно заранее, без запуска сессии: поле профиля, иначе `--dangerously-skip-permissions` среди собранных аргументов (это и есть bypass), иначе `permissions.defaultMode` из настроек самого claude.

Plan-режим в headless-claude, в отличие от TUI, **блокирует** правки и команды запросами разрешений — даже при bypass. Транспорт возвращает поведение терминала: если сессия запущена с bypass, обычные запросы на инструменты в plan-режиме он подтверждает сам (`🔓` в журнале), а до человека доходят только вопросы, сам план и запросы MCP. Без bypass plan-режим спрашивает, как и claude.

Выход из plan-режима — это одобрение инструмента `ExitPlanMode`: в чат приходит план и кнопки «Выполнять» / «Выполнять, спрашивая» / «Доработать». Согласие несёт с собой и смену режима (`updatedPermissions: setMode`), ровно как «how do you want to proceed» в TUI. «Выполнять» возвращает в bypass, если сессия была запущена с ним (claude не пускает в bypass сессию, стартовавшую без него), иначе — в acceptEdits.

Смены режима, которые claude делает сам (в том числе `dontAsk` у субагентов — их хуки транспорт отличает по `agent_id` и не учитывает), в чат не пишутся: только в журнал, а при `debug: on` — и в чат.

#### Кто поднимает сессию

- `claude -t telegram -P 2` — профиль по id; `-n rik` тоже находит его, пока алиас единственный; без того и другого — единственный профиль в конфиге. Профиль сам знает каталог, слот и чаты; `-C`, номер слота и `--tg-chat` переопределяют разово.
- `daemon: on` — демон поднимет профиль сам, как только к нему обратятся в его чате (само сообщение не теряется: оно доедет до сессии, когда та зарегистрируется).
- `/claude …` из чата выполняется всегда, даже при `daemon: off`: это явная просьба человека открыть окно на ПК. Профиль выбирается по `-P id` или `-n алиас`, без них — единственный, претендующий на этот чат, иначе единственный открытый в него; когда таких несколько, демон перечисляет их. `/rik /claude …` — то же самое для конкретного профиля.

#### Сессия на человека

При `multi: off` (по умолчанию) каждый участник чата получает **свой** claude: ключ — `(чат, топик, пользователь)`. Ответы уходят реплаем на сообщение, чтобы в группе было видно, кому отвечают; кнопки чужого диалога не нажимаются — на нажатие приходит «это чужой диалог». Один процесс транспорта — одно окно консоли — держит их все; второго окна на второго человека не открывается. Предел — `telegram-max-sessions` (8). При `multi: on` чат работает с одной общей сессией, и кнопки в ней общие.

Разговор, которому никто не писал `telegram-idle-hours` (1 ч; ход агента простоем не считается), закрывается с пометкой «💤 … сессия закрыта» и возвращает память; окно закрывается следом, если демон сможет поднять профиль заново (`daemon: on`). Следующее сообщение поднимает всё снова.

#### Окно консоли

Окно — журнал: в нём видно всё, включая вызовы инструментов, которых нет в чате. Читать из него ничего нельзя — набранное там никуда не уходит, и QuickEdit снимается, иначе клик внутри окна блокировал бы вывод и выглядел как зависшая интеграция. Продолжить разговор в терминале можно обычным `claude` и `/resume`. Закрытие окна крестиком уносит с собой все запущенные им claude: они состоят в job-объекте Windows с `KILL_ON_JOB_CLOSE` ([system/childjob.py](system/childjob.py.md)), так что сирот в памяти не остаётся.

#### Владение ботом

Telegram разрешает один `getUpdates` на токен: второй процесс получает 409. ccas на этом и строится: на токен — ровно один поллер, локально это лок `~/.claude-switcher/telegram/<bot_id>.lock`, глобально — сам Telegram. Разные ПК — разные боты. Токеном владеет демон; транспорт при старте поднимает его, если тот не запущен, и получает свои сообщения по локальному long-poll. Если демон пропал, транспорт забирает лок и опрашивает бота сам.

Демон нужен в автозапуске ровно тогда, когда есть профиль с `daemon: on` — отдельной настройки нет, `ccas profile set` сам заводит и снимает запись автозапуска (Run-ключ / `systemd --user` / launchd). При старте поллер пропускает накопившуюся очередь Telegram: команды, отправленные, пока никто не слушал, не выполняются задним числом.

#### Команды в чате

| Сообщение | Что происходит |
|---|---|
| `/алиас текст` | сообщение профилю; `/алиас` без текста — его статус |
| `/алиас! текст` | то же, но сначала прервать текущий ход (или открытый вопрос) — иначе сообщение ждало бы конца хода |
| `/алиас /new /plan текст` | несколько команд сессии подряд, затем промт: новая сессия, смена режима, старт работы |
| `/claude [-P id \| -n алиас] [слот] [-C каталог] [аргументы claude]` | на ПК открывается окно консоли с `claude … -t telegram -P id` |
| `/claude mcp list`, `/claude -p …`, `/claude --version` | выполняется разово, вывод в чат |
| `/projects` | известные каталоги проектов из `~/.claude.json` кнопками: 📁 выбрать, ▶ запустить там |
| `/cd <каталог>`, `/pwd`, `/ls [каталог]` | каталог, в котором стартуют новые сессии этого чата |
| `/sessions`, `/help` | живые сессии, справка |

Внутри сессии свои команды: `/stop` (прервать ход), `/new` (новая сессия в том же каталоге), `/clear`, `/exit`, `/kill`, `/status`, `/usage` (лимиты слота), `/cd` (перенести сессию в другой каталог — перезапуск с `--resume`, разговор сохраняется), `/pwd`, `/switch [слот]` (продолжить разговор на другом аккаунте), `/model`, `/mode`, `/save` (закрепить каталог и чат за профилем), `/help`; `!команда` выполняется в каталоге сессии (Windows — PowerShell, POSIX — bash), вывод показывается и передаётся claude в том же виде, что делает bash-режим TUI. Команд в одном сообщении может быть несколько — они выполняются по порядку, а первое слово, которое не команда сессии, начинает промт; после `/new`, `/clear`, `/cd` или `/switch` смена режима уходит новому claude аргументом запуска, промт — первым сообщением. Всё остальное — включая `/compact` — уходит claude как есть.

Три команды заканчивают разговор по-разному, и разница в том, что остаётся в чате:

| Команда | Сессия | Чат |
|---|---|---|
| `/new` | начинается заново в том же каталоге | остаётся как был, плюс строка «🧹 контекст очищен» |
| `/clear` | начинается заново | все сообщения агента удаляются — план, артефакты, ответы, вопросы, служебные строки |
| `/exit` | закрывается | остаются планы, артефакты и последний ответ агента, остальное удаляется |
| `/kill` | закрывается | остаётся как был |

**Файлы.** Файл, присланный с подписью `/rik …`, скачивается в каталог сессии, а его полный путь добавляется после текста промта; занятое имя получает номер — `notes (1).txt`. Альбом идёт одним промтом, если хотя бы у одного его файла есть подпись с алиасом; одиночный файл без алиаса никому не адресован. Файлы больше 20 МБ Telegram боту не отдаёт — об этом приходит строка в чат. В обратную сторону: артефакт, который агент сделал за ход, приходит после его ответа самим файлом (несколько — альбомами до 10), ссылка на claude.ai, если она была, — отдельным сообщением.

Удаляются только сообщения самого бота и только этой сессии: чужие реплики и написанное человеком не трогаются. Telegram разрешает боту удалять свои сообщения в течение 48 часов — то, что старше, останется в чате.

Упёршись в лимит, сессия предлагает кнопкой свободный слот. Свободных нет — она сама выбирает тот, что откроется раньше всех (это может быть и другой исчерпанный аккаунт, и текущий), объявляет время и ждёт, а в назначенный момент переезжает и продолжает. claude при этом жив: команды отвечают как обычно, `/status` показывает, чего и до каких пор ждём, а набранный текст уходит первым сообщением возобновлённой сессии (выигрывает последняя строка). `/switch`, `/cd`, `/new` и `/clear` ожидание снимают. Закрытие по простою (`telegram-idle-hours`) на такую сессию не распространяется: молчит агент, а не человек.

#### Глобальные настройки

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `telegram-token` | — | токен от @BotFather; в выводе маскируется |
| `telegram-console` | вкл | открывать окно консоли для сессий из `/claude` |
| `telegram-max-sessions` | 8 | сколько сессий держит один профиль одновременно |
| `telegram-idle-hours` | 1 | через сколько часов без обращений сессия закрывается; 0 — никогда |
| `telegram-prompt-timeout` | 0 | через сколько минут неотвеченный вопрос отклоняется; 0 — ждать |
| `telegram.users`, `telegram.roots` (в `config.json`) | пусто | белый список user_id и допустимые корни каталогов |

`ccas telegram test` проверяет токен и шлёт пробное сообщение; `ccas daemon status|start|stop` управляет демоном; `ccas doctor` показывает профили и состояние транспорта.

### Ctrl+C и раскладка клавиатуры

Ctrl+C в claude перестаёт работать на не-латинской раскладке (например, русской) и снова работает на английской. Это поведение самого Claude Code на Windows: в raw-режиме консоли нажатие приходит ему как символ, и «Ctrl+С» с кириллической буквой он не узнаёт. Обёртка тут не участвует — по клавиатуре она между консолью и claude не стоит и повлиять на это не может. Обход — переключить раскладку на английскую перед Ctrl+C или прервать генерацию клавишей Esc.

## Язык интерфейса

Определяется автоматически при установке: по `LANGUAGE`/`LC_ALL`/`LC_MESSAGES`/`LANG` на Linux и по `GetUserDefaultUILanguage()` на Windows. Поддерживаются `en` и `ru`.

```bash
ccas install --lang ru      # зафиксировать в конфиге
CCAS_LANG=ru ccas list      # разово
```

## Хранение токенов

Креды лежат открытым текстом, ровно как их хранит сам Claude Code: файл должен оставаться читаемым для процесса claude, поэтому зашифровать его на месте нельзя. Защита — права доступа: `chmod 600` на Linux, ACL только для текущего пользователя на Windows.

## Сборка

Зависимостей нет — только стандартная библиотека Python 3.10+ и PyInstaller на время сборки.

```powershell
powershell -ExecutionPolicy Bypass -File build\build.ps1
```

```bash
bash build/build.sh
```

В `build/` лежат три файла: `ccas.spec` — рецепт сборки для PyInstaller (вшивает `lang/*.json`, объявляет лениво импортируемые модули, отсекает лишнее и вычисляет имя артефакта), плюс два тонких скрипта-обёртки под bash и PowerShell. Расширение `.spec` обязательно: по нему PyInstaller отличает рецепт сборки от входного скрипта программы.

Версия в бинарнике берётся из тега. Скрипты сборки смотрят на `CCAS_VERSION`, а без неё — на `REF_TYPE=tag` и `REF_NAME_NORM`, которые toolkit выставляет при сборке по тегу; ведущий `v` и префикс пакета (`pkg/v1.2.0`) отбрасываются. На время сборки значение вписывается в `core/version.py`, после сборки файл возвращается как был — `ccas --version` в релизе совпадает с тегом, а в репозитории ничего не меняется. Локально: `CCAS_VERSION=1.2.0 bash build/build.sh`.

Всё временное складывается в один каталог `build/__pycache__/`: туда направлены и байт-код (`PYTHONPYCACHEPREFIX`), и рабочие файлы PyInstaller (`--workpath`). Рядом с исходниками не остаётся ни одного `__pycache__`, а сам каталог в `.gitignore` и удаляется безболезненно.

Имя артефакта — `ccas-<ос>-<архитектура>[.exe]`, результат кладётся в `dist/`:

```
dist/ccas-windows-x64.exe
dist/ccas-linux-x64
dist/ccas-macos-arm64
```

Бинарник PyInstaller линкуется с glibc сборочной машины, поэтому Linux-релиз лучше собирать в контейнере на старой базе.

## Тесты


## CI/CD и релизы

Релиз выпускается пушем тега `vX.Y.Z`. Порядок такой:

```
ci-cd.yml : get-branch -> gate -> ci (тесты)
                                   |
release.yml : await-ci ------------+
                 |
              prepare -> build (матрица ОС) -> release (создаёт GitHub Release)
                                                  |
ci-cd.yml :                                       +-> cd (деплой, если настроен)
```

`release.yml` ждёт проверку с именем `ci`, а job `cd` в `ci-cd.yml` ждёт `release` — цикла нет.

### Где задавать переменные

Оба workflow используют `environment: <ветка>`. Поэтому переменные нужно завести **либо** на уровне репозитория (`Settings → Secrets and variables → Actions → Variables`), **либо** в Environment с именем ветки, от которой ставится тег — обычно `main`.

### Переменные для `ci-cd.yml`

| Переменная | Значение | Зачем |
|---|---|---|
| `ACTION_TRIGGER` | `RELEASE` | **обязательно.** Только при этом значении job `ci` запускается на пуше тега |
| `CI_COMMAND` | `python3 -m unittest discover -s tests` | **обязательно.** Пустое значение — тесты не запустятся никогда, а релиз всё равно соберётся |
| `BUILD_COMMAND` | не задавать | сборку делает матрица в `release.yml` |
| `DEPLOY_*`, секрет `DEPLOY_KEY` | не задавать | деплоя на сервер нет, job `cd` останется выключенным |

`python3`, а не `python`: job `ci` не содержит шага `actions/setup-python` и пользуется тем интерпретатором, что есть на раннере.

Побочный эффект `ACTION_TRIGGER=RELEASE`: пуши в ветку CI не запускают (значение одно, `PUSH` и `RELEASE` взаимоисключающи). Pull request'ы тесты прогоняют всегда.

### Переменные для `release.yml`

| Переменная | Значение | Зачем |
|---|---|---|
| `BUILD_MATRIX` | `["ubuntu-latest","windows-latest","macos-latest"]` | включает матричную сборку; без неё `.exe` не появится |
| `RELEASE_FILES` | `dist/*` | что прикладывать к релизу |
| `PYTHON_VERSION` | `3.11` | версия для сборки (по умолчанию `3.11`) |
| `BUILD_ARTIFACT_COMMAND` | `SKIP_TESTS=true bash build/build.sh` | тесты уже прошли в `ci`; версию скрипт берёт из `REF_NAME_NORM` сам |
| `BUILD_ARTIFACT_PATH` | по умолчанию `dist` | можно не задавать |
| `BUILD_COMMAND` | **не задавать** | иначе сборка выполнится ещё раз на ubuntu и перетрёт артефакты матрицы |
| `PUBLISH_METHOD` | не задавать | публикации в npm/docker/packagist нет |
| `MULTIPLE_PACKAGES` | не задавать | тег имеет вид `vX.Y.Z` без префикса ветки |

Секреты не нужны: хватает автоматического `GITHUB_TOKEN`.

### Что попадёт в релиз

```
ccas-windows-x64.exe
ccas-linux-x64
ccas-macos-arm64
```

Имя вычисляет `build/ccas.spec` по `sys.platform` и `platform.machine()`, а не workflow; перебить можно переменной `CCAS_ARTIFACT_NAME`. `macos-latest` сейчас arm64 — если понадобится x64-сборка под Intel, добавьте в матрицу `macos-13`.

### Известное ограничение

`await-ci` использует `fail-on-no-checks: false`. Если `release.yml` стартует раньше, чем `ci-cd.yml` успевает зарегистрировать проверку `ci`, ожидание завершится сразу и релиз соберётся, не дождавшись тестов. Жёсткий гейт даёт `fail-on-no-checks: true`, но тогда релиз будет падать в конфигурациях, где `CI_COMMAND` не задан вовсе.
